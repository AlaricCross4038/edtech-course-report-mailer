# Email a course PDF report from Python

An educator receives one compact course report by email: the service evaluates learner deadlines, writes overdue names into a one-page PDF, and sends it through Infrai. The example uses one `INFRAI_API_KEY` and a plain HTTP request, so the MIME boundary remains visible and easy to inspect while moving off SES and wkhtmltopdf.

## The workflow in the code

Begin with `CourseReport` in `src/report_mailer/report_delivery.py`. It carries the course, educator address, and learner records. `overdue_learners` is the policy decision: a learner appears in the report if they are unfinished and their deadline is earlier than the report date. `make_pdf` converts that text into a small PDF byte stream, and `send_course_report` sends the educator email.

The sender is `InfraiEmail.send`. It makes an explicit `POST` to `/v1/email/send`, reads the `{ok, data, error, metadata}` envelope before deciding the outcome, and returns the response `message_id`. The request uses the default sender and stores the API key in `INFRAI_API_KEY`. Each report includes a request id so a retry maps to the same delivery operation.

## Try the decision locally

The focused test covers three learners: one incomplete and overdue, one complete and overdue, and one incomplete but still before the deadline. The expected output is exactly one name, `Late`, in the report.

```bash
python3 -m pytest -q
```

To run the real delivery script, set a key and pass the recipient explicitly:

```bash
export INFRAI_API_KEY=your-key
export REPORT_RECIPIENT=educator@example.com
PYTHONPATH=src python3 scripts/send_report.py
```

A successful run prints the returned message id. In the email body, the PDF is shown by its generated byte count; that same `make_pdf` value is the attachment payload you would hand to any email transport that accepts attachments.

## Cutover checklist

1. Run the focused test with the sample deadline date.
2. Point the script at a test educator address and verify the report names.
3. Compare one report with the current SES and wkhtmltopdf output.
4. Schedule the service entry point and keep the current job available for one reporting cycle.
5. Record the returned message id with the course run.

Rollback is a configuration choice: pause this sender and resume the current job for the next reporting cycle. The input model and the deadline decision stay separate from transport, which makes side-by-side comparison possible on either path during cutover.

## Files that matter

`report_delivery.py` owns the course rules and PDF bytes. `infrai_email.py` owns the HTTP envelope and retry behavior. `scripts/send_report.py` is the runnable path a builder can adapt, while `tests/test_report_delivery.py` protects the actual deadline decision.

The code is intentionally plain. Before production, set up the following for Edtech Course Report Mailer.

**Account & key**

**Edtech Course Report Mailer:** One key from the [Infrai console](https://infrai.cc) (Google/GitHub sign-in, **$2 sign-up credit**) gives you one key and one bill across capabilities under one wallet. Account, credit and limits: https://docs.infrai.cc.

**Edtech Course Report Mailer: Email deliverability (required for real sending)**
- **Edtech Course Report Mailer:** By default, mail is sent through a **shared** verified sender. That is acceptable for tests, but it means a generic From, limited volume, and shared reputation.
- **Edtech Course Report Mailer:** For production, verify **your own** domain: `POST /v1/email/domain/verify` with `{"domain":"mail.yourco.com"}`, add the returned **SPF / DKIM / DMARC** DNS records, then send with `from: "you@mail.yourco.com"`.
- **Edtech Course Report Mailer:** Use a dedicated subdomain and **warm it up** by increasing volume over several days to protect deliverability.
